MamaCare Technical Documentation

How a team of six builds and runs a multilingual pregnancy and postpartum companion for mothers in Nigeria: one mobile and web app, one admin panel, one API and one AI service.

Version 1.0 · November 2026 · For engineers, technical partners and anyone who wants to understand how the product is built.

1. Overview

MamaCare supports a mother from early pregnancy through the first year with her baby. It runs on Android, iOS and the web, in five languages: English, Yoruba, Igbo, Hausa and Nigerian Pidgin.

What the product does

  • Pregnancy mode: week-by-week guidance, a pregnancy overview, narrated audio in her language, walking and exercise, daily goals.
  • Postpartum mode: baby growth and measurements, a vaccination schedule, recovery and newborn care. The app switches mode when a mother records her delivery.
  • Mama AI: a conversational assistant for text, voice and photo questions, aware of her stage, pregnancy week and language.
  • Journal: private memories as text, voice notes and photos.
  • Care tools: appointments, medication reminders, weekly summaries and a mental wellbeing check-in.
  • Community: discussions, groups, events, polls and private messages between mothers.
  • Plans: free features plus Pro and Max subscriptions with a 7-day free trial, and a referral programme.

3. Team and ownership

The team has six people. Each role owns a clear area, so every part of the system has one accountable owner and nobody waits on a committee.

Figure 1. Team structure. The product manager sets scope; each engineer owns one area end to end.

RoleOwnsMain repositories
UI and Product ManagerProduct scope, user research, UI design and design system, acceptance criteria, release priorities.Design files, backlog
Frontend engineer 1The mobile and web app: screens, navigation, offline behaviour, translations, in-app purchase flow.mamacare-mobile
Frontend engineer 2The staff admin panel and web deployment: dashboards, content tools, user and subscription management.mamacare-admin, web hosting
Backend engineerThe API, database schema, business rules, payments and the AI service.mamacare-server, mamacare-ai
QA engineerTest strategy, automated and exploratory testing, device matrix, release sign-off.Tests in every repository
DevOps engineerCloud infrastructure, pipelines, secrets, monitoring, backups, cost and capacity.Pipeline and infra configuration

Why this shape

  • Two frontends, one backend: there are two very different clients (a consumer app and a staff tool). One backend engineer keeps business rules in a single place and avoids duplicated logic.
  • QA as its own role: a health product needs someone whose only job is to try to break it, across many Android devices and three languages.
  • DevOps as its own role: releases, secrets and capacity are where small teams get hurt, so they have a dedicated owner.
  • Product and design combined: at this size, one person holding both keeps decisions fast and the interface consistent.

Working agreements

  • Every change is reviewed by someone other than its author before it merges.
  • The API contract is agreed before frontend and backend work starts. It is versioned (/api/v1) and changes are additive by default.
  • A feature is done when it is tested, translated in all five languages, and QA has signed it off.
  • Releases are small and frequent. Anything that touches payments, authentication or health data gets extra review.

4. Code bases

The system lives in four repositories. Each has one owner, one runtime and one deployment path.

RepositoryWhat it isRuntimeDeploys to
mamacare-mobileThe app for Android, iOS and the web, from one code base.TypeScript, React Native (Expo)App stores, over-the-air updates, web hosting
mamacare-adminThe staff admin panel: users, content, community moderation, subscriptions, analytics.JavaScript, Next.jsWeb hosting
mamacare-serverThe main API and the only service that talks to the main database.Java 17, Spring BootManaged container platform
mamacare-aiThe AI assistant service: prompts, guardrails, conversation memory.Python, FastAPIContainers (reverse proxy, API, worker, cache, database)

Why several repositories instead of one

  • Different runtimes and release speeds. The app ships through stores and over-the-air updates, the API ships continuously, the admin panel ships on its own. One repository would force them onto one cadence.
  • A security boundary around the AI service. Model provider keys live only in mamacare-ai. The app never talks to it directly.
  • Clear ownership. One engineer per repository means no shared, orphaned code.
  • Small, fast pipelines. Each repository builds and tests only what it contains.

What it costs, and how we manage it

  • Contract drift between app and API. Managed with a versioned API, additive changes and the rule that the server never trusts the client for access decisions.
  • Duplicated types across repositories. Accepted: the contract is small and stable, and tooling for sharing types would add more weight than it removes at this size.
  • One app code base for three platforms instead of three native apps. Platform-specific code lives in clearly named files (.web.tsx for the web) and stub modules for features the browser lacks.

6. Architecture

MamaCare is a modular monolith for business logic (one API, organised into feature modules) with one separate service for AI. Clients talk only to the main API. The API is the single source of truth for identity, data and access rules.

Figure 2. System architecture. Solid boxes are services we run; dashed boxes are third parties.

Principles

  • The server decides. Access, limits and plan rules are enforced on the API. The app mirrors them for a good experience but is never trusted.
  • Stateless API. Any instance can serve any request, so the platform can add or remove instances freely.
  • One gateway to AI. The app calls the main API; the API adds trusted context (plan, stage, week, language) and forwards to the AI service. Model keys never leave the AI service.
  • Work that can wait, waits. Reminders, summaries, clean-up jobs and AI follow-ups run in the background instead of blocking a request.
  • Verify, never assume. Store receipts, store notifications and payment webhooks are checked cryptographically before they change anything.

8. Data model

The main database holds about sixty persistent entities, grouped below. Every record that belongs to a user is stored with that user's identifier and filtered by it on every query, so one user can never read another's data.

Figure 3. Data model overview. Boxes group related entities; the user is the centre of every relationship.

Modelling rules

  • User-scoped by default. Every personal record carries the owning user and is queried with it.
  • Entitlements are the single source of truth for access. A user can hold several entitlements (store subscription, web payment, referral reward, admin grant). The API picks the one in force and exposes it through one access endpoint.
  • Money and receipts are append-friendly. Store purchases and payments are kept as records; we store fingerprints of signed receipts rather than the receipts themselves.
  • Schema changes are versioned migrations applied automatically at deploy, so every environment has the same shape.
  • Personal media is private. Files are served through short-lived signed links, and AI photos are removed after 24 hours.

10.2 Asking Mama AI

Figure 6. A Mama AI question. The app never contacts the AI service or the model provider directly.

  • Trusted context (stage, pregnancy week or baby age, language, plan) is added by the API from stored data, not taken from the app.
  • Guardrails are part of the prompt: no diagnosis, no prescriptions, and a clear instruction to seek urgent care for danger signs.
  • Photos are uploaded to private storage, passed to the model through short-lived links, and deleted after 24 hours.

10.3 Subscriptions

Figure 7. Purchase and renewal. Steps 7 and 8 happen without the app, so access stays correct even if the user never reopens it.

  • Account label: each purchase carries a label tied to one MamaCare account, so a leaked receipt cannot be claimed by someone else.
  • Referral rewards: a friend's free trial earns nothing; the person who invited her receives a month of the same plan when the friend's first real payment succeeds.
  • Web payments follow the same shape: Paystack confirms the payment to the API, which records it and creates the entitlement.

11. API design

TopicConvention
StyleREST over HTTPS with JSON. Resources are grouped by feature (for example journal, community, appointments).
VersioningEvery route lives under /api/v1. Changes are additive; breaking changes get a new version.
AuthenticationBearer access token on every request except sign-in, sign-up, code verification and signed provider callbacks.
Current user"Me" endpoints read the user from the token. Clients never send a user identifier for their own data.
ErrorsStandard HTTP status codes with a JSON body (title, detail, status). 401/403 for identity and permission, 402 for a feature that needs a plan, 429 for too many requests.
IdempotencyRequests that must not run twice (for example an AI question) carry a client-generated request identifier.
ListsPaged with page and size; sizes are capped on the server.
WebhooksStore notifications and payment confirmations are accepted only with a valid signature and ignored otherwise.

Example: asking what the user can access

One small endpoint tells the app everything it needs to decide what to show:

GET /api/v1/me/access
{ "locked": false, "pro": true, "plan": "PRO", "expires_at": "2026-12-04T12:03:42Z", "source": "APPLE" }

The app renders from this answer; the server enforces the same rules independently on every protected route.

12. Security and privacy

AreaPractice
TransportHTTPS everywhere with strict transport security. Origins are allow-listed for browser access.
Accounts and sessionsPasswords are stored as salted hashes. One-time codes are stored hashed and expire. Sign-in and code endpoints are rate limited. Signing out or resetting a password revokes sessions on the server.
AuthorisationRole-based access for staff (user, manager, admin). Personal data is always filtered by the owning user. Paid features are enforced on the server.
PaymentsStore transactions and notifications are verified with the stores' signatures. Purchases are tied to one account. We keep fingerprints of receipts, not the receipts.
Data minimisationOnly city and state are kept for location, never an exact address, and never shown to other users.
MediaPrivate storage; short-lived signed links; type and size validation; AI photos deleted after 24 hours.
AI safetyGuardrails against diagnosis and prescriptions; danger signs trigger advice to seek urgent care; content moderation for community posts.
SecretsKept in the cloud secret manager and environment configuration, never in source control or in the app.
MonitoringCrash and error reporting, structured logs and audit lines for sensitive events such as subscription transfers.

15. Performance and scale

  • Horizontal by design. The API is stateless, so adding instances raises capacity until the database becomes the limit.
  • The database is the first bottleneck. We reduce load before adding hardware: a bounded connection pool, a short cache of sign-in lookups (a few seconds), and filtering at the database rather than in code.
  • Protecting the user experience. Reads time out and retry once; slow or failing networks show a connectivity notice instead of an endless spinner.
  • Heavy work is isolated. AI calls run in their own service with their own queue and database, so a slow model cannot starve the main API.
  • Measure, then spend. A repeatable load test runs against a staging copy; capacity decisions follow its results.

Scaling path

StepChangeTrigger
1Move the database to a larger dedicated tierDatabase CPU or memory regularly high
2Share rate limits and caches across instances (Redis)More than a few API instances in steady use
3Add a read replica for reporting and community feedsRead traffic dominates database load
4Split a module into its own service if it needs separate scalingA feature's load or release cadence diverges

16. Trade-offs and roadmap

Deliberately left out for now

  • Full offline editing. Reading cached data and a clear connectivity notice come first; queued offline writes need a native storage layer and careful conflict rules.
  • A shared cache for rate limits. Limits are per instance today; they become shared when traffic needs it.
  • Multi-region hosting. One region keeps the system simple while the audience is concentrated.
  • Fully automated translation review. Every language is reviewed by a native speaker before release, which is slower but safer for health content.

Roadmap themes

  • Offline queue for journal, medications and appointments.
  • Native-quality icons and a refreshed visual system across platforms.
  • More languages and more recorded audio per week.
  • Richer postpartum content and tools.
  • Capacity upgrades following load-test results.

17. Glossary

TermMeaning
EntitlementA record that says a user has a plan until a date, and where it came from (store, web payment, referral, admin).
Access gateThe server check that blocks paid features for users without an entitlement.
JWTJSON Web Token: a signed token that proves who the user is.
Refresh tokenA longer-lived token used only to get a new access token.
OTA updateOver-the-air update: new app code delivered without a store release.
Modular monolithOne deployable application organised into well-separated feature modules.
GatewayA service that receives requests, adds trusted information and forwards them to another service.
GuardrailA rule in the AI prompt or pipeline that limits what the assistant may say or do.
MigrationA versioned, repeatable change to the database schema.
IdempotentSafe to repeat: doing it twice has the same effect as doing it once.
